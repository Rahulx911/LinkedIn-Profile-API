# LinkedIn Profile API

Given a LinkedIn profile URL, returns structured JSON (name, headline, location,
about, experience, education, skills, certifications, languages, profile images).

No browser is used anywhere at runtime. The service talks to LinkedIn's internal
Voyager API directly over HTTP, authenticated with a session cookie, the same way
LinkedIn's own web frontend does.

## How this was reverse engineered

LinkedIn's profile page is a single-page app that fetches its data from
`/voyager/api/...` endpoints after the initial HTML loads. Opening a profile page
with DevTools' Network tab open and filtering for `voyager` shows the request
that actually loads the profile:

```
GET https://www.linkedin.com/voyager/api/graphql
    ?includeWebMetadata=true
    &variables=(memberIdentity:ACoAA...)
    &queryId=voyagerIdentityDashProfiles.b5c27c04968c409fc0ed3546575b9b7a
```

Two things worth calling out about this, because most older writeups on
"LinkedIn scraping" describe a different (now largely retired) REST API with
separate endpoints per section (`/identity/profiles/{id}/profileView`,
`/positions`, `/skills`, ...):

- **LinkedIn now serves the whole profile as one persisted GraphQL query.**
  Loading a profile page fires exactly one `voyager/api/graphql` call for the
  top card, About, positions, education, skills, certifications, and languages —
  confirmed by watching network traffic while scrolling through a full profile;
  no additional per-section calls fired.
- **That query takes an internal member URN (`memberIdentity`), not the public
  username in the URL.** Viewing your own profile doesn't show how this URN
  gets resolved, because the server already knows who you are from the session —
  there's no visible resolution call for your own profile. For anyone else's
  profile, the client here resolves the URN itself: it fetches the public
  profile page HTML (authenticated) and pulls the URN out of the
  server-rendered hydration JSON with a regex (`urn:li:fsd_profile:...`,
  see `app/linkedin/client.py::resolve_urn`). This avoids depending on a
  separate lookup endpoint or a decoration ID, both of which are undocumented
  and change over time.

**What's confirmed vs. what still needs a live test pass:** the GraphQL
endpoint and query ID above were captured from a real, logged-in browser
session. The URN-resolution regex and the exact `$type` field names used in
`app/linkedin/parser.py` were designed from the normalized-JSON conventions
LinkedIn's Voyager API uses elsewhere, but verifying them against a real
response requires an authenticated call — which has to be made from your own
machine with your own session cookie, not by an automated tool. Run
`python scripts/inspect_raw.py <public_identifier>` after setup (see below) to
print the real `$type` values and confirm/adjust the mapping in `parser.py`.

## Architecture

```
Client
  │  POST /api/v1/profile {"url": "..."}
  ▼
FastAPI app (app/main.py)
  │  validate URL, check cache
  ▼
VoyagerClient (app/linkedin/client.py)
  │  1. resolve_urn()      -> GET /in/{username}/       (authenticated HTML, regex for URN)
  │  2. fetch_profile_raw() -> GET /voyager/api/graphql   (persisted query, normalized JSON)
  ▼
parser.py -> our own ProfileResponse schema (app/models.py)
```

## Setup

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# then fill in LI_AT_COOKIE (and optionally JSESSIONID) in .env — see comments in that file
```

Run locally:

```bash
uvicorn app.main:app --reload
```

Interactive API docs (auto-generated by FastAPI): `http://localhost:8000/docs`

Inspect the raw LinkedIn response to verify/tune the parser against a real profile:

```bash
python scripts/inspect_raw.py <public_identifier>
```

Run tests (these use a synthetic fixture, not live LinkedIn calls):

```bash
pytest
```

## API

### `POST /api/v1/profile`

Request:

```json
{ "url": "https://www.linkedin.com/in/some-person/" }
```

Response `200`:

```json
{
  "public_identifier": "some-person",
  "name": "Jane Doe",
  "headline": "Software Engineer at ExampleCorp",
  "location": "Bengaluru, India",
  "about": "Building things with code.",
  "experience": [
    {
      "title": "Software Engineer",
      "company": "ExampleCorp",
      "location": "Bengaluru, India",
      "date_range": { "start": "2022-6", "end": null },
      "description": "Working on backend systems."
    }
  ],
  "education": [ ... ],
  "skills": [ { "name": "Python" } ],
  "certifications": [ ... ],
  "languages": [ ... ],
  "profile_images": [ { "url": "https://media.licdn.com/..." } ]
}
```

Error responses share one shape (`{"error": "...", "detail": "..."}`) and map
LinkedIn's own responses to sensible HTTP status codes:

| Status | Cause |
|---|---|
| 400 | Input isn't a LinkedIn profile URL |
| 401 | Session cookie missing/expired/checkpointed |
| 403 | Profile private / out of network / account restricted |
| 404 | Profile doesn't exist, or URN couldn't be resolved |
| 429 | LinkedIn is rate-limiting this account |

Liveness check for deployment platforms.

## Security

- The LinkedIn session cookie lives only in environment variables (`.env`
  locally, platform env vars in deployment) — never in the repo. `.gitignore`
  excludes `.env` and any `debug_output/` from `scripts/inspect_raw.py`.
- No LinkedIn credentials or cookies are ever logged.

## Known limitations

- **Account risk.** LinkedIn's Terms of Service prohibit automated scraping,
  and can restrict the account whose cookie is used here. This was built and
  tested against [my own primary account / a secondary account — update this
  line based on which you used], accepting that tradeoff for the scope of this
  challenge. A production system would use a dedicated, disposable account.
- **Rate limiting.** Requests are cached in-memory per profile
  (`PROFILE_CACHE_TTL_SECONDS`) to reduce repeat hits, but there's no
  cross-instance cache or distributed rate limiter.
- **Session expiry.** `li_at` cookies expire (typically ~1 year, but can be
  invalidated sooner by a security checkpoint). When that happens the API
  returns `401` and the cookie needs to be refreshed manually.
- **Visibility limits.** Profiles outside the authenticated account's network,
  or with restricted visibility settings, may return partial data or a `403`.
- **Profile images.** LinkedIn's CDN URLs for profile photos are time-limited/
  signed; returned URLs may expire after some time rather than being permanent.
- **Parser field mapping.** See "How this was reverse engineered" above — the
  exact `$type`/field names in `parser.py` should be confirmed with
  `scripts/inspect_raw.py` against a real profile before relying on this in
  production.
